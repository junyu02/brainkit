# INSTALLER.md — 安装器的逻辑与原理

写给**不打算读 `install.mjs` 的人**：这个仓库的所有者，以及任何被派来动它的 agent。

`install.mjs` 约 4000 行。你不需要读它，但你需要知道下面这些——**尤其是「它不做什么」那一节，那里有一条最容易被想当然搞错的**。

---

## 1. 它装什么

一条命令把这套系统在一台 Mac 上装好。它会往四个地方写东西：

| 位置 | 写什么 | 性质 |
|---|---|---|
| `~/.config/second-brain/` | 配置、环境变量、安装状态 | 全新建立 |
| vault（你的笔记库） | 系统骨架目录 + 由 publisher 部署的代码 | **可能已经住着你的笔记** |
| `~/.local/bin/` | 两个垫片脚本 | **公共柜子，别人的工具也在这** |
| `~/Library/LaunchAgents/` | 四个后台服务的 plist | 系统目录 |

后两个位置的风险最高：**它们不是我们的地盘**。如果那里已经有同名文件，安装器会先把原件收起来——而**那份备份是唯一副本**。

---

## 2. 核心模型：先声明，后改动

一句话：**任何一次改盘之前，先把"我要改什么、它原来是什么样"写进一份记录，然后才动手。**

这份记录叫**事务清单**（transaction manifest），存在 `~/.config/second-brain/recovery/<事务id>/`。它记下每一项：路径、改之前长什么样、改之后应该长什么样、备份放在哪。

为什么这样做：如果安装在中途炸了（磁盘满、服务起不来、断电），系统需要知道**该退回到哪里**。没有这份记录，"撤销"就只能靠猜。

**安装失败时会自动回滚**——这是自动的，不需要你做任何事。它按记录逐项还原，还原完再检查一遍磁盘确实回到了原样。

---

## 3. 它不做什么（最重要的一节）

### `recover` 只诊断，不修复

```
node install.mjs recover
```

这条命令**不会修好任何东西**。它读现场、告诉你发生了什么、哪些文件被动过、原件在哪、每一步该怎么做——**然后什么都不碰**。

为什么砍掉修复能力：做了十三轮复核，每一轮都能找到它在错误的时刻删错东西的新场景。**一个 80% 情况好用、20% 情况悄悄删掉你文件并报告"成功"的自动修复，比没有更糟。**

所以现在你需要手动做的是：把被替换的文件放回去、删掉安装新建的文件、`launchctl bootout` 停掉已启动的服务、删掉 `install-state.json` 才能重装。`recover` 会把这些逐条打印给你。

> **注意：仓库里有两个 `recover`，不是一回事。**
> `publish.mjs --recover` 是发布器的恢复，那个**会**动手修。
> `install.mjs recover` 只诊断。看到 `recover` 先确认是哪一个。

### `uninstall` 只出计划，不删除

和 `recover` 同样的理由，同样的结局：两轮独立复核在执行段找到同一族的数据后果缺陷（删除没绑定到刚校验的对象、位置校验只看形状并集、vault 根只按字符串印证），预先写死的止损线触发，**执行那一半关掉了**。它打印会删什么、保留什么、为什么，然后退 1，**一个文件都不动、一个服务都不停**。要真卸载，用第 6 节的手工步骤。没有 flag 能打开它。

### 两个 daemon 脚本不再是安装器

`brain-watch.mjs` 与 `brain-clip.mjs` 的 `install` / `start` 子命令**已关闭**，函数体连同只被它们用到的 helper 一并删除（写 `process.execPath` 进 plist 的那段是重点）。它们不是无害的重复入口，而是会覆盖正确配置的第二套安装器：写版本化 node 路径、绕过垫片校验、绕过 watch root 显式选择。现在跑它们只会向 stderr 打印一行指向 `install.mjs` 的提示并退 1。`package.json` 的 `watch:start` 同步移除。

**唯一安装入口是 `node install.mjs install`。** 两个脚本保留的 `stop` / `status` 仅供人工排障——installer 与 publisher 从不消费它们的输出，服务快照一律来自现场 `launchctl print gui/$UID/<label>`。

### 它不编译 `brain-clip-helper`（装了 clip 之后你得自己跑一条命令）

安装器**不编译**这个 Swift helper，切片 8 之后**整个 repo 里也没有任何脚本会编译它**——原先那条惰性编译路径唯一的入口是已删除的 `brain-clip.mjs install`。

所以**装了 clip 组件之后，服务能起来但干不了活**：handler 启动时发现 helper 不存在会直接退出，并打印该跑的命令。自己跑一次：

```sh
swiftc "<vault>/00-系统/scripts/bin/brain-clip-helper.swift" -o "<vault>/00-系统/scripts/bin/brain-clip-helper"
```

`<vault>` 换成你的 vault 根。这条命令与 `brain-clip-handler.mjs` 缺失时打印的那条是同一条。

**安装器预检的 `swiftc` 就是为这一步准备的**：选了 clip 组件时，preflight 会先 `xcrun --find swiftc`、再退回 PATH 查找，找不到就报错让你 `xcode-select --install`。**它不是安装器自己要用**——安装器全程不调用 swiftc，检查的是你稍后手工编译时会不会缺工具。

这是一处已知能力缺口，见第 8 节 `artifacts.clip_helper` 那条：**没有生产者写基线，所以卸载不删它；也没有生产者编译它，所以安装不给你**。两头都缺的是同一个生产者。

### 它不写 vault 内的代码

vault 里的脚本一律由 `publish.mjs` 部署。安装器只负责调用它、以及创建它需要的目录。**安装器里没有第二套复制逻辑。**

### 它不迁移、不重排你的笔记

装进一个已有 vault 时，规则全是否定式的：只补缺失的目录、不覆盖已有的、不改已存在目录的权限、不动任何用户文件。已经有的 `.project-map.json` 只做格式校验，一个字节都不改。

## 4. 三条安装分支

安装器根据 vault 现场自动判断走哪条，你不用选：

| 分支 | 现场 | 行为 |
|---|---|---|
| **A** | 全新 vault | 建目录，跑 `publish --bootstrap` 建立基线 |
| **B** | vault 已存在，但从没部署过代码 | 同上，但先列出将被替换的目标路径让你确认 |
| **C** | 代码已部署过，但安装状态没了 | **跳过 bootstrap**，直接 `publish --check` |

分支 C 的典型来源：卸载过（卸载有意保留代码）、手工跑过 publisher、配置目录被清理过。

**为什么必须单列 C**：publisher 在清单已存在时会无条件拒绝 bootstrap。如果安装器不认这个分支，"装 → 卸 → 再装"必然失败，而且失败点在配置已经写完之后。

## 5. `upgrade`

```
node install.mjs upgrade [--pull|--no-pull] [--adopt-shims] [--verify-online]
```

`--no-pull` 是默认值：不加任何 flag 时它**不会**去 `git pull`。

## ⚠️ 它现在不升级任何东西

`upgrade` 的**改盘那一半是关掉的**。它做检查、告诉你会改什么、给你手工步骤，然后退 1。

**为什么**：两轮独立复核在改盘路径上查出同一族的数据后果缺陷。最后一次是：成功收口被打断时，会先删掉事务清单仍然声称存在的备份，**恢复材料真实丢失，而报告说成功**。切片预先写死的止损线就是为这种情况准备的——不重新谈判，直接降级。

**没有开关能把它打开。** 没有 flag，没有环境变量。一个带开关的禁用只是多一步的同一个命令。

改盘的机械（步 5–10、回滚、收口）**留在代码树里**，仍然被测试守着——那部分修复是复核验证过的真资产，删掉等于把已验证的东西再做一遍。它只是从 CLI 不可达。

**重新打开的条件**（两条都要）：`tests/test-install.mjs` 里三个 `KNOWN-FAIL` 标记全部转绿，**且**独立复核通过。单靠 todo 转绿不算。

---

### 它现在做什么

| 步 | 做什么 |
|---|---|
| 1–2 | 状态校验、身份校验、抢锁、worktree 必须干净 |
| 3 | `--pull` 时拉取并交接给新 HEAD 的安装器 |
| 4 | 跑全量测试套件，必须全绿 |
| — | **然后停下**，打印会改什么 + 手工步骤，退 1 |

打印的内容：`publish --check` 的现状、需要变动的垫片、会重渲染的 plist、当前在跑的服务，以及逐条手工命令。

**手工路径能覆盖的只有 vault 代码和服务重启**（`publish.mjs` + `launchctl kickstart`）。垫片和 plist 的重建只有被禁用的那条路做得安全——如果报告说它们需要变动，那部分现在没有安全的手工做法，报告会直说而不是让你自己去改 `~/.local/bin`。

### 目标形态（禁用中，留作参考）

规格 §8.1 的十步：重建垫片 → `publish --check` → 发布 → 重渲染 plist、只重启原来在跑的服务 → 验收 → 记录 commit、消费事务。失败时把生产退回升级前。

其中第 9 步的验收**从来就不含组件 smoke**（明确延期到真机端到端那批），而第二轮复核进一步判定：已实现的那部分验收「用邻近信号代替了 authority」——只看 `publish --check` 的一个字段而不是它的完整终态、只验 plist 的宽松契约而不是本次写入的 hash、只验服务非空而不是它从本次写的 plist 加载。这三条是重新打开前必须补齐的。

### 动手之前必须同时成立的六件事

1. `install-state.json` 存在——没装过就没有升级这回事
2. 状态是 `installed`——上一次没跑完的机器该去 `recover`，不是升级
3. **记录里的 repo 和 vault 路径，今天仍然解析到它自己**——见下
4. 你是**从当初安装的那个 clone** 里跑的（比对 realpath）
5. `install-state.json` 和 `brainkit.conf` **都**指向同一个 vault——一个可编辑的文件不能给自己作证
6. 拿得到安装锁；锁被活着的进程持有就停，**并且不去碰那个锁文件**

第 3 条是第 4、5 条盖不住的那一种：**把 vault 搬走、在原路径留个符号链接**，两份记录里的字符串一个字都没变、互相也仍然一致，变的只有磁盘。此时升级会用旧身份去重建一个不同的目录。所以每个记录下来的 root 都要重新 resolve 一次，必须还等于它自己。

（记录路径**整个不见了**是另一回事，由 vault 检查负责报，不归这一条。但如果连它的父目录都没了、根本没法 resolve，这里会点名拒绝，而不是甩一个文件系统错误给你。）

外加 worktree 必须干净。任何一条不成立都是拒绝，磁盘零写入。

### 它不做什么

- **不 stash、不 reset、不切 branch。** worktree 脏它就停，让你自己处理，没有 `--force`。
- **不动 vault 里的用户内容**——vault 里的代码由 publisher 更新，你的笔记一个字节都不碰。
- **不修。** 和 `recover` 一样，看不懂的现场它报告然后退出。
- **不会替你启动你自己停掉的服务。** 见下。
- **不会因为是"升级"就放松垫片接管的门槛。** 见下。

### 垫片：升级不比安装宽松

第 5 步会重建垫片（node 垫片即使 target 没变也重建）。判定规则和安装时是同一套，没有"升级嘛，覆盖就覆盖了"这种事：

| 现场 | 行为 |
|---|---|
| 已经是当前版本 | 不写 |
| 带 brainkit marker 的旧垫片 | 备份后覆盖 |
| **不带 marker 的文件**（你自己的脚本） | **停下来**，要你加 `--adopt-shims` |
| 不带 marker + `--adopt-shims` | 备份后接管，摘要里点名 |

第三行是重点：`~/.local/bin` 是公共柜子。**那份备份是你脚本的唯一副本**，位置在 `recovery/<事务id>/` 下。

### 服务：只重启原来在跑的

第 8 步会保存"升级开始时哪些服务是 loaded"，然后**只重启这一批**。你自己停掉的服务，升级后**依然是停的**——它的 plist 会被更新到新版本，但不会被 bootstrap。

理由：升级不该替你改变机器的运行状态。你停掉某个服务通常是有原因的。

### `--pull` 之后跑的不是你敲命令时的那个版本

`--pull` 成功后**当前进程不再往下走**：它放掉锁，用 `<repo>/install.mjs`（刚拉下来的那份）起一个子进程，把原来的参数加上 `--no-pull --resumed-after-pull` 传过去，然后原样返回子进程的退出码。

理由：旧安装器驱动新模板和新 publisher，正是这一步要避免的组合。

`--resumed-after-pull` 是交接跟自己说的话，帮助里没有，你不需要敲。

### 「repo 新、生产旧」怎么读

`--pull` 会把你的 clone 推到新 HEAD。**此后任何一步拒绝，你的机器就停在「盘上的代码是新的、跑着的还是旧的」**。这是合法状态，不是损坏。

这个状态最终会有**三种**形态，措辞已经定死要严格分开，不许混用——把它们读成同一件事会让你的下一步做错：

失败报告分成**两层**说，因为它们是两个不同的 authority：安装器自己的那层（垫片、plist、服务），和 publisher 拥有的那层（vault 里的代码和 manifest）。

**本地层**（先说）：

| 情况 | 报告怎么说 |
|---|---|
| 回滚干净 | 垫片、plist、服务都回到升级前 |
| 回滚干净，只是 recovery 目录清不掉 | 同上，外加「这是清理问题不是损坏」 |
| 回滚没能完成 | **生产状态未知**，去跑 `recover`，附具体是什么挡住的 |

**publisher 层**（后说）：

| 情况 | 报告怎么说 | 你该做什么 |
|---|---|---|
| 从没报告改过 vault | 没有它的东西要撤 | 处理问题后重跑 |
| 改过，`--recover` 成功 | **repo 是新的，生产已回滚** | 直接重跑 `upgrade` |
| 改过，但本地层没恢复完 | **它的恢复被有意跳过**，附 backup 路径和手工顺序 | 先解决本地层，再按给出的顺序手工恢复 |
| 改过，`--recover` 自己失败 | **生产半新半旧**，附失败原因和 backup 路径 | **别再跑 upgrade** |

两处值得单独说：

- 「发布从未开始」不是「什么都没发生」的同义词。步 5 排在步 6 前面，所以步 6 硬停时垫片**已经被重建过又还原回去了**，那是一个真做过的还原动作。（规格里没写，从步骤顺序推出来的。）
- **本地层没恢复完时，安装器不会去动 publisher 那层。** 在第一层已知没完成的情况下改第二层，只会把一层停住变成两层各恢复一半。它会保留 backup 并把手工顺序打印给你。

怎么看清自己在哪：`node install.mjs doctor` 报的是生产的状态，`git -C <repo> log -1` 报的是代码的状态。

## 6. `uninstall`

```
node install.mjs uninstall [--purge-config] [--purge-logs] [--non-interactive --yes]
```

## ⚠️ 它现在不删除任何东西

`uninstall` 的**执行那一半是关掉的**。它读状态、打印它会删什么保留什么、给你手工步骤，然后退 1。**它不停服务、不删文件、不取锁。**

**为什么**：两轮独立复核在执行段查出同一族的数据后果缺陷——删除动作没有绑定到刚刚校验过的那个对象（共享复验与逐项 `unlink` 之间还能改）、位置校验用的是所有产品形状的并集（可以让 `plists.watch` 指向 `brainkit.conf` 并把它删掉）、vault 根只按字符串印证（根被换成 symlink 时 `rmdir` 会跟着走）。切片预先写死的止损线就是为这种情况准备的——不重新谈判，直接降级，没有第三轮。

**没有开关能把它打开。** 没有 flag，没有环境变量。一个带开关的禁用只是多一步的同一个命令。

执行的机械（确认、取锁、身份复验、停服务、逐项删除）**留在代码树里**，仍然被测试守着——那些修复是复核验证过的真资产。它只是从 CLI 不可达：`runUninstall` 停在计划，`uninstallExecute` 没有调用点。

**重新打开的条件**：R2-F1 至 R2-F7 全部关闭，**且**独立复核 PASS。逐条见第 8 节。

**要真的卸载，用下面的手工步骤**——那是当前唯一完整的办法，不是补充说明。

### 它会怎么判定（计划输出里仍然生效）

下面这套判据现在**只决定打印什么**，不决定删什么。只有**安装状态记录过、且现在仍然对得上**的东西会被列进 "Would remove"：

删除授权同时绑定三样东西，缺一不可：**记录**里有内容基线、**内容**仍等于那个基线、**位置**是安装器自己会创建的地方。

| 目标 | 对得上的判据 |
|---|---|
| 四个 plist | **与安装时记录的 sha256 一致**（label/mode 契约不再参与卸载判定，见下） |
| node / wrapper 垫片 | **既有 brainkit marker，又与记录的 hash 一致** |
| 配置（仅 `--purge-config`） | 与记录的 sha256 一致 |
| 安装状态文件 | 排在最后，**且只有前面全部成功才会被列为删除** |

**位置这一条是独立的**：`install-state.json` 是可编辑文件，它写的路径只是一个声明，不是许可。每一行都要落在安装器注册表声明的形状里（和 recovery 用的是同一套模型），出界的行保留并说明。

**任何一项对不上就归入 "Would keep"** 并逐项写明原因。**注意**：R2-F2 证明「位置」这一条只校验了所有产品形状的**并集**——构造一条 `plists.watch` 指向 `brainkit.conf` 的记录能通过它。这正是执行段被禁用的原因之一；计划输出里这条判据仍然会照上表打印，**但不要把它当成安全边界**。

**「判定做两次」现在只做一次**：第二次判定（紧邻 unlink 的复验）属于被禁用的执行段。而且 R2-F1 证明即使那一半跑起来，复验与逐项 `unlink` 之间仍有窗口。

### 计划里不会列进 "Would remove" 的东西

- **`~/.local/bin` 目录本身，永不删除、永不遍历。** 那是公共柜子，里面有 `uv`、`claude` 这些别人的东西。它只按两个精确文件名操作。
- **被 `--adopt-shims` 接管过的第三方原件**：留在 recovery 目录里，卸载既不还原也不删除，路径会打印给你。
- **配置**（`brainkit.conf`、`clip.env`、`observe.env`、routing、memory 索引）：默认保留，要删得加 `--purge-config`。**即使加了，被你改过的配置仍然保留并报告**，不强删。
- **`brain-clip-helper`**：规格说按 `install-state.artifacts.clip_helper.sha256` 比对，但**安装器从来没写过那个字段，也从来没编译过这个文件**。没有记录就不满足「记录过且对得上」，所以不删。（见第 8 节偏差清单。）
- **旧版安装留下的 plist**。plist 的 sha256 是后加的；在那之前装的机器，`state.plists` 里只有路径没有 hash，计划会把它列成 "Would keep"，原因写 `watch has no recorded content baseline to verify against`。谁会遇到：**从公开快照 `c268307` 装的机器**就是这个格式（那份快照早于本次改动）。执行段禁用之后这一条不再有实际后果——**对谁都不删**——但它说明即使执行段重开，那种记录也删不掉。

### 手工卸载（当前唯一完整的办法）

`uninstall` 不会执行这些，你自己跑。装了哪些组件按 `install-state.json` 的 `components` 看，或者直接对四个名字都试一遍（没装的那条 `bootout` 会说找不到，无害）。

```sh
# 1. 停服务。每个装过的组件各一次。
launchctl bootout gui/$(id -u)/com.second-brain.clip
launchctl bootout gui/$(id -u)/com.second-brain.observe
launchctl bootout gui/$(id -u)/com.second-brain.sunday
launchctl bootout gui/$(id -u)/com.second-brain.watch

# 2. plist
rm -f ~/Library/LaunchAgents/com.second-brain.{clip,observe,sunday,watch}.plist

# 3. 垫片（只有这两个名字，目录本身别动——里面有别人的东西）
rm -f ~/.local/bin/brain-node ~/.local/bin/brain-watch-wrapper.sh

# 4. 安装状态
rm -f ~/.config/second-brain/install-state.json

# 5. 配置与 memory 索引（想留配置就跳过这一步）
rm -f ~/.config/second-brain/{brainkit.conf,vault-routing.json,clip.env,observe.env}
rm -f ~/Library/Application\ Support/brainkit/memory/{MEMORY.md,MEMORY-knowledge.md,MEMORY-experience.md,MEMORY-project.md,MEMORY-persona.md,MEMORY-archive.md,MEMORY-notes.md}
```

第 5 步的 memory 索引之前漏在这份清单外（R2-F7）。它们和 `~/.config/second-brain/*` 一样记在 `managed_files` 里，`--purge-config` 会删它们，所以手工清单不列就不等价。路径与 `install.mjs` 的 `MEMORY_INDEXES` 常量一致。

**vault 不用动**：本命令不碰它，日志（`~/Library/Logs/second-brain/`）想删自己删。

### 三件卸载后会让你困惑的事

1. **vault 里的代码还在**，但没有任何 LaunchAgent 指向它了，它不会自己运行。想彻底删就手动删那个目录。
2. **`brain-clip-helper` 不会自己回来。** 之前那个「手工跑一次 `brain-clip.mjs` 就会重新编译回 vault」的惰性构建，唯一入口是 `brain-clip.mjs install`，已随切片 8 关闭第二安装器一并删除。现在 helper 缺失时，clip handler 会打印该跑的 `swiftc` 命令，不会有任何东西背着你重建它。
3. **在同一个 vault 上重装会跳过 publisher bootstrap、直接 check。** 因为 manifest 还在。那是分支 C，是预期行为不是故障。

摘要里这三句都会打印，不用读这份文档才知道。

### 什么时候它连计划都不出

- **状态不是 `installed`**（`installing` / `upgrading` / `recovery-required`）：那台机器上有一个活事务仍然声称拥有这些文件。它退 2，不打印计划。先去 `recover`。
- **没有 `install-state.json`**：退 1，没装过就没有卸载这回事。

下面这两条属于**被禁用的执行段**，现在从 CLI 走不到（`uninstallExecute` 里仍在，仍被测试守着）：服务从别的 plist 加载时拒绝停任何东西并退 2；`--purge-config` / `--purge-logs` 的确认（交互式问一次，非交互或 `--non-interactive` 必须给 `--yes`）。

`--purge-logs` 现在**只影响计划里列出哪些日志路径**。判据（仍然只作用于打印）是从 plist 正文读出它自己声明的那两个路径，另外还夹四道：

- **只有本次真要删的 plist 才有资格提名日志**。一份已经判为「不是我们的」或「被改过」的 plist 是被保留的对象，不是授权的来源。
- **路径必须落在 `~/Library/Logs/second-brain/` 里**。plist 是文本文件，可以写任何绝对路径；出界的一律不删。
- **跨 plist 合并后去重**。真实模板让多个服务共用一个 `daemon.log`，不去重会删一次、然后把第二次的 `ENOENT` 报成失败并退 2。
- **声明了但根本不存在的日志，列出来但不算失败**。装了没跑过的服务就是这样：plist 写着 `daemon.log`，磁盘上从来没有过。它会以「保留」出现在摘要里（原因写明服务从未创建），**不影响退出码**——没东西可删不是漂移。它仍然是一行，因为悄悄从清单里消失的路径事后没人能对账。

同一个目录下别人的文件、子目录、以及目录本身，一律不碰。

**关于 vault 内那四个空目录**：执行段里有一步会对 `00-系统/scripts/{bin,cli,daemon,lib}` 调 `rmdir`（只删空目录）。**它现在不会跑**，所以本命令对 vault 真正做到了一样都不碰——**是因为执行段整个禁用了，不是因为那段代码不存在**。它还带着两个已知缺陷，重开前要一起修：`drifted.length === 0` 把默认保留的配置和 absent log 这类 policy keep 算作「没有保留项」，所以默认卸载也会删那四个目录，同时摘要还在说 vault 未触碰（R2-F6）；`verifiedVaultRoot` 只比对字符串，vault 根被换成 symlink 时 `rmdir` 会跟着走到别的目录（R2-F4）。

## 7. 退出码

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 1 | 需要你做点什么再来（有安装在跑、需要 `--yes` 确认、前置条件不满足）。**`upgrade` 和 `uninstall` 的正常路径都退 1**：它们打印计划和手工步骤，改盘/执行那一半是关掉的，「你还得自己动手」正是这个码的意思 |
| 2 | 磁盘上的东西无法解释，拒绝继续（路径不安全、文件类型不对、清单损坏） |
| 3 | 有一个没做完的安装，已打印手工处置步骤 |

**退 2 之后，现场要么从没被动过，要么已经被同进程回滚干净。** 绝大多数这类拒绝发生在写入之前。

**一个例外，别漏掉**：iCloud 冲突副本那一类的拒绝**发生在骨架建好之后**（原因见第 8 节「iCloud 冲突副本」那条）。正常情况下它会自动回滚干净，但**如果在建骨架和回滚之间被强杀或断电，你的 vault 里会留下一副空骨架**。退 2 之后如果发生过异常中断，去第 8 节确认一下。

## 8. 已知限制（如实列出，不粉饰）

- **`recover` 不修复**，见第 3 节。
- **两处规格判据在代码里没有生产者**，卸载因此用了比规格弱的判定，如实记在这里：
  - `install-state.artifacts.clip_helper.sha256` —— 规格要卸载按它比对 `brain-clip-helper`，但 `artifacts` 恒为空对象，安装器也从不编译这个文件。**没有基线就不删**，helper 保留。**另一面在第 3 节**：既然没人编译它，装完 clip 也不会自动有这个文件，得自己跑一次 `swiftc`。缺的是同一个生产者。
  - ~~plist 没有记录 hash~~ —— **已修**。安装侧现在为每个 plist 记录 sha256，卸载只按 hash 判定，和垫片、配置走同一条判据。`assertPlistContract` 在卸载路径上**完全不再调用**：它对任何带我们 label、我们 mode 的文件都放行——包括被改写了 `ProgramArguments` 的那份，独立复核正是用这样一个样本让旧判据删掉了用户的文件——所以它不能收窄 hash 已经决定的事，留着只会让人误以为它还在出力。
  - **旧版 state 里的 plist 只有路径没有 hash**。那种记录会被枚举、保留、并在摘要里说明原因（`no recorded content baseline`）。执行段禁用后这一条不再有实际后果——对谁都不删。
- **`uninstall` 不执行**，见第 3、6 节。计划照出，一个文件不动。**重开条件：下面七条全部关闭，且独立复核 PASS。** 两轮复核报告与探针存档在 `.omc/audit/`。
  - **R2-F1 阻断/数据后果** — 共享复验与逐项 `unlink` 之间仍能改文件：删除动作没有绑定到刚刚比对过 hash 的那个对象。
  - **R2-F2 阻断/数据后果** — `managedShapes` 校验的是所有产品形状的并集，没绑定产品类别：`plists.watch` 指向 `brainkit.conf` 并记录其正确 hash 就能在没给 `--purge-config` 的情况下删掉配置。
  - **R2-F3 重要** — 初始 absent-log 的 policy keep 会盖过服务 `bootout` 时新落下的日志：`--purge-logs` 退 0、日志留下、state 已删。
  - **R2-F4 阻断/数据后果** — `verifiedVaultRoot` 只印证路径字符串；vault 根被换成 symlink 后 `rmdir` 会删掉别的目录里同名的四个空目录，错误还被 catch 吞掉。
  - **R2-F5 阻断** — `components` 含 watch 但 `plists.watch` 为 null 时，服务列表静默丢行：一次 launchctl 都不读，删 state、退 0，还打印「no LaunchAgent points at it」。
  - **R2-F6 重要/数据后果** — 摘要与文档声称 vault 未触碰，但正常路径会 `rmdir` vault 内四个空目录；`drifted.length === 0` 把 policy keep 当作「没有保留项」。
  - **R2-F7 重要** — 手工清理清单漏了本机 memory index（`~/Library/Application Support/brainkit/memory/MEMORY*.md`），因此不等价于完整 `--purge-config`。**已在第 6 节补上。**
- **`upgrade` 不改盘**，见第 5 节。这是本安装器目前最大的一处「能力比规格弱」。两个待关闭的窗口：
  - **F2 — 成功收口不是可中断协议**：在清单被标记 spent 之前就删掉它仍声称存在的备份，中断会真实丢失恢复材料；且此时 state 已是 `installed`，`recover` 因此拒绝诊断。
  - **F4 — 验收用邻近信号代替 authority**：publisher 只看一个 `state` 字段而不是完整终态、plist 只验宽松契约而不是本次写入的 hash、服务只验非空而不是从本次写的 plist 加载。
  - 组件 smoke 另按裁决延期到真机端到端那批，不计入这两个窗口。
- **`upgrade` 被强杀或断电会留下 `status=upgrading`**。事务在正常失败时会回滚；被外力打断则不会。此时 `recover` 会认出这是一次升级、给出把 `install-state.json` 恢复成 `installed` 的具体做法（**绝不会叫你删它**），然后才让你重跑 `upgrade`——少了恢复那一步，`upgrade` 会因状态不是 `installed` 再次拒绝，两个命令互相推诿。
- **进程接力只在调用层面被验证过**。测试能证明的是：子进程执行的确实是 `<repo>/install.mjs`、带着防重入标记、父进程交接之后不再编排任何东西。**证明不了新 HEAD 的 `install.mjs` 本身是对的**——那需要两个真实不同的版本一起跑，属于真机端到端。
- **iCloud 冲突副本的拒绝发生在建骨架之后**，不是之前。规格要求安装器不得自己扫 vault、只能消费 publisher 的检查结果，而那次检查必须在骨架存在后才能跑。后果：这一类失败走的是回滚而不是拒绝——**回滚被证明是干净的，但如果在建骨架之后、回滚之前崩溃，你的 vault 里会留下一副空骨架**。这和"写之前就拒绝"不等价。
- **真机端到端验收未完成**。所有试跑都在临时目录，没有在干净账户上真跑过完整的装→用→卸流程。
- **安装器生成的配置，日常 CLI 目前不读**。`brain-write` 等脚本仍从 `~/.claude/` 读配置。这是个已知的未接线状态。
- **安全网覆盖不完整**。上一次全量普查的结论是：代码里 119 处安全检查，测试能确实盯住的是 77 处；其余的关掉之后测试不会变红。清单在 `tools/guard-census.mjs` 跑出来的结果里。**这两个数字是 `upgrade` 落地之前的**——全量一跑几个小时，之后每个切片只普查自己新增的那几处（用 `--lines`），没有再重跑全量。

## 9. 出事了怎么办

1. **先跑 `node install.mjs recover`**，它会告诉你现场是什么状态。它不会动任何东西，跑它是安全的。
2. 按它打印的步骤手工处理。原件位置它会给。
3. **`recovery/` 目录下的东西不会自动消失。** 安装当场失败且自动回滚跑完时会自己清掉；被外力打断（断电、强杀）的不会。确认无误后自己删。
4. 如果 `~/.local/bin` 里你原来的脚本被接管了，它的原件在 `recovery/<事务id>/adopted-shims/` 下——**那是唯一副本，删之前想清楚。**

## 10. 给要改这个安装器的 agent

- 设计规格在 `.omc/plans/brainkit-p2-spec-v0.3-FROZEN.md`，**但 §14 的 A2–A6 修订推翻了正文的一部分**，尤其 A2 作废了所有"恢复会自动还原"的承诺。先读 §14 再读正文。
- 改动前跑 `node tools/guard-census.mjs`，它会把每处安全检查逐个关掉、看测试抓不抓得住。**你新增的每一处拒绝都必须是 `caught`。** 全量一跑几个小时，所以只想问自己这批新增的话用 `--lines <行号,行号> --out <另一个文件>`——默认那个输出文件是全仓库的常驻普查结果，别把一个切片的几行混进去。
- 历轮复核报告在 `.omc/audit/`。反复出现的缺陷是同一族：**注释声称了一个不变量，代码只实现了它的一部分**。写注释前先确认代码哪一行在保证那句话。
